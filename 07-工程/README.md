# 07-工程 · 工程实现文件

> 定位：**规格的实现物**。前端页面、后端代码、接口联调工程等实际运行产物，与文档体系同仓库管理（本目录纳入统一 Git 版本控制，保证「契约」与「实现」同版本演进）。

---

## 一、工程文件在依赖链中的位置

```
02-约束(工程约定) → 03-规格(行为契约) → 07-工程(实现) → 04-验收(断言跑在实现上)
```

工程文件不是文档，它是 03-规格 的下游翻译、04-验收 的检查对象。文档体系通过两个接口与它咬合：

- **02-约束 写入「工程约定」**：目录结构、命名规范、模块划分原则——文档管工程的结构；
- **04-验收 跑在工程产物上**：断言脚本、接口联调记录——文档管工程的证明。

## 二、内部组织原则

工程内部按**业务模块**分割，镜像 03-规格 的模块划分（如 production / quality / equipment），不按技术类型堆文件：

```
07-工程/
├── production/        报工/派工（对应 spec-production 相关条目）
├── quality/           检验/不良（对应 spec-quality 相关条目）
├── equipment/         点检/维修（对应 spec-equipment 相关条目）
├── shared/            跨模块通用（布局、权限指令、通用组件）
└── api/               接口契约（前后端/系统间边界）
```

- 模块划分依据是 **02-约束 的组织模型与业务域**，不是页面类型；规格分割决定工程分割；
- **页面 = 一组规格的集合**：每个页面维护一行「规格映射」（页面 → 实现的 spec ID 列表），验收与变更都靠它索引；
- 接口契约与数据模型从 **02-约束 的主数据规范**（物料编码、批次规则等）推导，不得在工程里另起一套。

## 三、与验收的联动

- 页面出问题 → 通过规格映射定位到覆盖的 spec 条目，不翻整个页面；
- 改一个页面之前 → 先看它覆盖哪些规格，评估影响面；
- 验收层的断言跑在 07-工程 的产物上，跨系统（ERP/PLC/设备）部分走接口联调记录。

## 四、演进说明

工程规模变大后，可按需拆出独立仓库（07-工程 仅保留引用或子模块指针），届时在 05-决策 记录该变更。
