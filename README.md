# MES 原型规格 · 文档驱动产品设计工作流（探索项目）

> 一句话定位：从「PRD → vibe coding → HTML」的**高不确定性**，转向「md 规格体系 → 按规格生成 → 逐项验收」的**文档驱动工作流**。
>
> 项目实例：汽车零部件模具制造企业的 MES 制造执行系统（拉延模/翻边模/冲孔模，工艺链 设计 → CNC → 热处理 → EDM 精加工 → 钳工装配 → 试模）。

---

## 一、项目动机：PRD 到 HTML 的不确定性

传统工作流是：**PRD（意图层）→ vibe coding（AI 自由发挥）→ HTML 原型**。这个链条存在系统性不确定性：

| 问题 | 表现 |
|---|---|
| 意图与结构脱节 | PRD 描述业务逻辑和功能需求，**不描述页面结构、交互、状态**，AI 只能自行脑补 |
| 同源不同形 | 同一个 PRD，两次 vibe coding 产出两个不同的原型，无法建立「标准答案」 |
| 缺少中间验收层 | PRD 与 HTML 之间没有可逐项核对的规格，评审只能凭感觉 |
| 结构漂移 | 没有信息架构（IA）约束、没有页面 ID 约定，页面与组件命名随意，后期对不上 |
| 异常状态缺失 | PRD 通常不写空态/错误态/权限态/边界，AI 默认不生成 |
| 返工闭环长 | 改一次需求 → 重新 vibe coding → 又一轮不确定性，成本随轮次放大 |

**核心判断**：不确定性来自「意图」与「实现」之间缺少一个**可评审、可复用、可逐项验收的中间规格层**。本项目探索的正是这一层——用 md 文档把它建起来。

## 二、探索方向：让确定性回到文档层

用**文档化规格**替代 Axure/HTML 承担的三大职责——**页面跳转、页面布局、异常状态**——让任何 AI（或设计师）仅凭文本即可生成、评审、复刻可交互原型。

- 规格只保留不可被其他形式替代的信息：**页面清单（IA）、逐页布局、跳转流、状态矩阵**；
- 角色权限、业务数据属于项目实例（且多为运行时自定义配置），**不写死进规格**；
- 视觉规范独立成层，项目规格只写「遵循哪个规范、覆盖了哪些」。

## 三、方法论：模板三层（L0 / L1 / L2）

| 层 | 文件 | 职责 | 维护频率 |
|---|---|---|---|
| L0 全局规范 | `global-design-system.md`（模板，独立维护） | 视觉/组件/动效规范，跨项目复用 | 跨项目，几乎不变 |
| L1 通用模板 | `prototype-spec.md`（模板） | 原型规格骨架：页面/布局/跳转/状态 | 方法升级时才改 |
| L2 项目实例 | `03-规格/mes-prototype-spec.md` | 只填本项目事实（页面、布局、跳转、状态、权限快照） | 随项目迭代 |

模板三层解决「怎么表达」，下面的分层体系解决「文件放哪、谁约束谁」。

## 四、分层体系：一份文件的归属由「它在决策链中的位置」决定

不按文档主题分（组织、排期、质量……），按三个问题分：**回答「为什么」还是「是什么」？变一次的成本高不高？是「规则」还是「实例」？**

### 4.1 八层一览（00–07）

- **00-素材**（预留）：前期调研原始材料（访谈、现状梳理）。是分层的**输入端**，蒸馏后降级为历史档案，不参与体系运转；
- **01-意图**：PRD、SRS。为什么做、范围边界、成功标准。允许模糊，但要有边界（明确不做什么）；
- **02-约束**：组织/角色、工厂模型（工厂→车间→产线→工位）、主数据规范（物料/批次/SN/编码）、业务规则（班次/设备能力/插单优先级）。**工厂本体模型，变更影响全系统**，必须走 05-决策 留痕；
- **03-规格**：按模块的契约（报工/派工、检验/不良、点检/维修……）。每条可判定真伪，从 02-约束 推导且不得违反；
- **04-验收**：逐条回溯规格 ID，记录结果与证据。MES 比普通网站多一类验收——**接口联调**（与 ERP/PLC/设备对接），证据是联调记录而非页面断言；
- **05-决策**：变更决策记录（ADR）。约束层变更、模板升级、结构变迁必须留痕；
- **06-归档**（预留）：联调记录、验收证据、旧版文档。历史，不再维护；
- **07-工程**：规格的实现物（前端页面、后端代码、接口联调工程），与文档同仓库管理，纳入统一 Git 版本控制（内部组织见 `07-工程/README.md`）。

### 4.2 层是结构，时间是过程——两者正交

层回答「这份文件是什么、怎么被使用」，时间回答「它什么时候被创建、什么时候活跃」。**每层文档都有产生时间和活跃期，但活跃期不等于产生期**：

- 02-约束 在调研/规划期产生，此后长期活跃，只在受控变更时动；
- 04-验收 的**标准**在建设期就写好，**执行**在联调/上线期发生；
- 05-决策 从第一次变更起活跃，越到后期越厚。

### 4.3 契约 vs 执行：素材与证据不属于任何层

五层文档管的是**契约/标准**，不是过程记录：

| 阶段产物 | 性质 | 归属 |
|---|---|---|
| 前期调研纪要、访谈记录 | 素材（原料） | 00-素材，是分层的输入 |
| 组织架构、排产规则 | 契约 | 02-约束 |
| 接口联调的**验收标准** | 契约 | 04-验收（建设期写好） |
| 联调时实际跑出的**记录** | 证据（执行结果） | 06-归档 或进系统 |
| 某天某产线的具体排期 | 实例（执行结果） | 进系统，不进文档 |

**素材和证据是契约的输入端和输出端，不属于任何层。** 若把素材留在分层里，文档会跟着调研天天变——分层的价值恰恰在于它是**冻结后的契约**。运行数据（具体排期、实际报工）高频变更，进系统不进文档。

### 4.4 依赖链与三条联动规则

```
02-约束 → 03-规格 → 07-工程 → 04-验收
```

- **约束优先**：规格违反约束，是规格错，不是约束错——除非在 05-决策 显式豁免；
- **验收可回溯**：验收条目必须能回溯到规格 ID；凭空出现 = 隐式需求，补回规格再谈验收；
- **变更三向联动**：改规格必改验收；验收暴露问题回改规格或约束，并记一条决策。这是文档驱动的护城河——vibe 模式改需求是「重新摇骰子」，文档驱动改需求是「定点手术」。

### 4.5 时间轴：各阶段产生与消费什么

```
调研期   素材（访谈/现状/痛点）→ 不属于分层，是输入
   ↓ 蒸馏
规划期   01-意图 + 02-约束（草案）
   ↓ 定稿
设计期   02-约束（定稿）→ 03-规格 + 04-验收（标准部分起草）
   ↓ 契约驱动
实施期   03-规格 驱动 07-工程 开发
   ↓ 执行
联调/上线   04-验收执行 → 产出证据（联调记录 → 06-归档）
   ↓ 维护
运行期   05-决策全程活跃；运行数据进系统
```

## 六、工作流：本项目主张的生成与验收路径

```
01-意图/（项目章程、SRS）
        │
        ▼
03-规格/mes-prototype-spec.md（L2 原型规格：页面清单/逐页布局/跳转/状态/权限）
        │  组装 prompt（模板第九章，含"生成前必答"检查清单）
        ▼
AI 按规格生成 HTML 低保真原型（8 页面，ID 与规格一致）
        │  评审三列法（已满足/未满足/存疑）自检 → 对照 04-验收 逐项验收
        ▼
07-工程/（实现产物，模块镜像规格，页面维护规格映射）
        │
        ▼
Figma 插件（mes-prototype-figma）→ 可编辑、可交互原型
```

关键约束（写入规格与 prompt）：

- 页面 ID 小写英文语义化，与 HTML hash / Figma Frame 一致，**不得改名**；
- 不得新增未列入规格的页面；未标【待确认】的文案不得自行发挥；
- 权限按演示初始数据实现，且不把权限写死进业务逻辑；
- 生成前先逐条复述规格（确认理解一致）再动手——防漂移成本最低的动作。

## 七、快速开始

1. 读 `01-意图/00-项目章程-v0.1.md` 了解项目全貌；
2. 读 `03-规格/mes-prototype-spec.md` 了解原型规格（8 页面：登录/工位执行端/排产工作台/审核工作台/生产看板/追溯中心/工单列表/项目台账）；
3. 用规格的「prompt 组装模板」交给 AI 生成/评审 HTML 低保真原型；
4. 对照 04-验收 逐项验收（自动断言 + 人工复核）；
5. 用 `mes-prototype-figma/` 插件在 Figma 中生成可编辑原型（用法见该目录 README）。
