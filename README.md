# MES 原型规格 · 文档驱动产品设计工作流（探索项目）

> 一句话定位：从「PRD → vibe coding → HTML」的**高不确定性**，转向「md 规格体系 → 按规格生成 → 逐项验收」的**文档驱动工作流**。
>
> 项目实例：汽车零部件模具制造企业的 MES 制造执行系统（拉延模/翻边模/冲孔模，工艺链 设计 → CNC → 热处理 → EDM 精加工 → 钳工装配 → 试模）。

---

## 一、项目动机：PRD 到 HTML 的不确定性

传统工作流是：**PRD（意图层）→ vibe coding（AI 自由发挥）→ HTML 原型**。这个链条存在系统性不确定性：

| 问题 | 表现 |
|---|---|
| 意图与结构脱节 | PRD 描述业务逻辑和功能需求，**不描述页面结构、交互、状态**，AI 只能自行脑补 |
| 同源不同形 | 同一个 PRD，两次 vibe coding 产出两个不同的原型，无法建立「标准答案」 |
| 缺少中间验收层 | PRD 与 HTML 之间没有可逐项核对的规格，评审只能凭感觉 |
| 结构漂移 | 没有信息架构（IA）约束、没有页面 ID 约定，页面与组件命名随意，后期对不上 |
| 异常状态缺失 | PRD 通常不写空态/错误态/权限态/边界，AI 默认不生成 |
| 返工闭环长 | 改一次需求 → 重新 vibe coding → 又一轮不确定性，成本随轮次放大 |

**核心判断**：不确定性来自「意图」与「实现」之间缺少一个**可评审、可复用、可逐项验收的中间规格层**。本项目探索的正是这一层——用 md 文档把它建起来。

## 二、探索方向：让确定性回到文档层

用**文档化规格**替代 Axure/HTML 承担的三大职责——**页面跳转、页面布局、异常状态**——让任何 AI（或设计师）仅凭文本即可生成、评审、复刻可交互原型。

- 规格只保留不可被其他形式替代的信息：**页面清单（IA）、逐页布局、跳转流、状态矩阵**；
- 角色权限、业务数据属于项目实例（且多为运行时自定义配置），**不写死进规格**；
- 视觉规范独立成层，项目规格只写「遵循哪个规范、覆盖了哪些」。

## 三、方法论：三层文档分层

| 层 | 文件 | 职责 | 维护频率 |
|---|---|---|---|
| L0 全局规范 | `global-design-system.md`（模板，独立维护） | 视觉/组件/动效规范，跨项目复用 | 跨项目，几乎不变 |
| L1 通用模板 | `prototype-spec.md`（模板） | 原型规格骨架：页面/布局/跳转/状态 | 方法升级时才改 |
| L2 项目实例 | `mes-prototype-spec.md` | 只填本项目事实（页面、布局、跳转、状态、权限快照） | 随项目迭代 |

配套文档链（`docs/`）：**项目章程 → SRS 需求规格 → 概要设计 → 排产算法原理 → 多层级制造模型 → 技术实现方案 → 版本迭代与平滑切换 → 低保真线框 → 数据字典**，从需求到实现形成可追溯链条。

## 五、工作流：本项目主张的生成路径

```
docs/ 项目文档（章程/SRS/概要设计）
        │
        ▼
mes-prototype-spec.md（L2 原型规格：页面清单/逐页布局/跳转/状态/权限）
        │  组装 prompt（模板第八章，含"生成前必答"检查清单）
        ▼
AI 按规格生成 HTML 低保真原型（8 页面，ID 与规格一致）
        │  评审三列法（已满足/未满足/存疑）自检
        ▼
Figma 插件（mes-prototype-figma）→ 可编辑、可交互原型
```

关键约束（写入规格与 prompt）：

- 页面 ID 小写英文语义化，与 HTML hash / Figma Frame 一致，**不得改名**；
- 不得新增未列入规格的页面；未标【待确认】的文案不得自行发挥；
- 权限按演示初始数据实现，且不把权限写死进业务逻辑。

## 六、快速开始

1. 读 `docs/00-项目章程-v0.1.md` 了解项目全貌；
2. 读 `mes-prototype-spec.md` 了解原型规格（8 页面：登录/工位执行端/排产工作台/审核工作台/生产看板/追溯中心/工单列表/项目台账）；
3. 用规格第九章「prompt 组装模板」交给 AI 生成/评审 HTML 低保真原型；
4. 用 `mes-prototype-figma/` 插件在 Figma 中生成可编辑原型（用法见该目录 README）。
